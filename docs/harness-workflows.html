팀은 필요한 만큼만

기본값은 한 에이전트입니다. 에이전트를 나눌 이유가 있을 때만 추가로 생성합니다.

약 2배에이전트를 하나로 합친 뒤 빨라진 속도(한 고객사)
80% 이상필요할 때만 불러오게 해서 줄인 Claude Code 지시문
30~50개도구가 이보다 많으면 맞는 도구를 덜 고릅니다
에이전트가 많으면 생기는 일
  • 넘길 때마다 정보가 빠집니다
  • 역할이 겹치고 책임자가 없습니다
  • 지시끼리 충돌합니다
  • 느려지고, 전체 품질은 아무도 보지 않습니다
이럴 때만 나눕니다
  • 한 에이전트가 맡기에 양이 너무 많을 때
  • 여러 일을 동시에 해야 할 때
  • 도구를 잘못 고르거나 지시가 충돌할 때
  • 예 서로 독립된 조사, 결과 검증
합칠 때는 이렇게
  • 채점용 예시 10개를 먼저 만듭니다
  • 한 번에 하나씩 합칩니다
  • 점수가 떨어지면 되돌립니다
  • 같은 과제를 두 번 이상 실행합니다

에이전트 대신일하는 순서는 스킬로, 실행은 도구(MCP)로, 참고 자료는 지식 베이스로 옮깁니다

용어 정리

하네스는 AI에게 일을 시키는 구조 전체입니다. 역할·기준, 맥락, 도구, 작업 절차, 가드레일 다섯 요소로 이루어지고(하네스 엔지니어링), 워크플로우는 그중 작업 절차입니다. Claude Code에 다이내믹 워크플로우로 진행해 달라고 요청하면 Claude가 이 작업 절차를 스크립트로 직접 작성합니다. 코드나 설정은 필요 없습니다.

작업 절차에 반복해 쓰이는 패턴은 여섯 가지입니다. 앞의 둘은 큰 일을 나눠 빠르게 처리하는 방법이고, 뒤의 넷은 결과를 믿을 수 있게 만드는 방법입니다. 조합은 Claude가 하므로 결과를 검토할 수 있을 정도만 알면 됩니다.

이 기능은 Claude Code 전용입니다. Codex는 서브에이전트로 대응하며, 역할을 미리 정의해 두고 불러 씁니다.

왜 이 여섯 가지인가

Claude가 워크플로우를 작성할 때 참조하는 Claude Code 내장 가이드(/workflow-authoring)는 워크플로우를 쓰는 목적을 세 가지로 듭니다. 한 에이전트로는 감당하기 어려운 큰 일을 나눠 빠르게 처리하는 것, 내보내기 전에 틀린 결과를 거르는 것, 빠짐없이 찾는 것입니다. 이 가이드는 일을 나누는 기본 방식(펼치기, 파이프라인)과 결과를 다지는 방식(적대적 검증, 심사위원단, 바닥까지 반복, 다각도 수색)을 제시하고, Claude는 이 부품을 조합해 작업 절차를 만듭니다. 패턴 자체는 도구에 묶이지 않습니다. Codex에서는 요청에 패턴과 역할을 적으면 서브에이전트가 같은 배치로 움직이므로, 아래 각 패턴의 요청 예는 두 도구에 그대로 쓸 수 있습니다.

목적패턴막는 문제
큰 일을 나눠 빠르게펼치고 합치기, 파이프라인한 에이전트가 조각을 순서대로 처리하며 기다리는 시간
틀린 결과 거르기적대적 검증, 심사위원단그럴듯하지만 틀린 결과가 그대로 통과하는 것, 한 안만 계속 고쳐 쓰는 것
빠짐없이 찾기바닥까지 반복, 다각도 수색정해진 횟수나 한 가지 검색 방식이 놓치는 부분

목적과 패턴의 짝은 이 가이드의 정리입니다. Anthropic 해설 글(2026년 6월 2일)은 같은 성격의 패턴을 다른 이름으로 소개합니다(분류 후 실행, 펼치고 종합, 적대적 검증, 생성 후 거르기, 토너먼트, 끝날 때까지 반복).

1펼치고 합치기 (Fan-out)
검수와 수정 단계가 이렇게 움직입니다

일을 독립된 조각으로 펼쳐 여러 에이전트가 동시에 처리하고, 결과를 하나로 모읍니다. 여섯 관점의 검수도, 파일별 수정도 이 방식이라 사람이 순서대로 기다릴 필요가 없습니다.

요청 예"자료를 관점별로 나눠 동시에 검수하고, 결과를 하나로 모아 줘"

2파이프라인 (Pipeline)
여러 단계 작업이 이렇게 흐릅니다

조각마다 단계를 독립적으로 통과합니다. 빠른 조각은 앞 단계가 끝나는 즉시 다음 단계로 넘어가므로, 가장 느린 조각을 전원이 기다리는 일이 없습니다.

요청 예"파일마다 초안, 검토, 정리를 따로 진행하고 끝난 파일은 바로 다음 단계로 넘겨 줘"

3적대적 검증* (Adversarial verification, 애드버세리얼 베리피케이션)
검증 단계가 이렇게 움직입니다

고친 에이전트와 별개의 에이전트가 결과를 깨뜨리려고 달려듭니다. 자기 답을 자기가 후하게 평가하는 자기 편향을 막는 장치입니다. 그래도 통과하면 신뢰도가 올라갑니다.

요청 예"수정본은 고치지 않은 에이전트가 반박하듯 검증하게 해 줘"

* 머신러닝의 GAN(생성적 적대 신경망, Goodfellow 외, 2014)과 같은 발상입니다. 만드는 쪽과 판별하는 쪽을 나눠 서로 겨루게 합니다. 다만 GAN은 두 신경망을 함께 학습시키는 방법이고, 이 패턴은 학습 없이 이미 만든 결과를 검증하는 절차입니다.

4심사위원단 (Judge panel)
정답이 하나로 정해지지 않은 설계에 씁니다

서로 다른 관점으로 초안 여러 개를 동시에 만들고, 별도 심사 에이전트들이 점수를 매깁니다. 1등안을 뼈대로 삼고 나머지 안의 좋은 점을 가져와 합칩니다.

요청 예"서로 다른 관점으로 초안 세 개를 만들고, 다른 에이전트가 채점해 1등안에 장점을 합쳐 줘"

5바닥까지 반복 (Loop-until-dry)
빠짐없이 찾아야 하는 일에 씁니다

찾는 작업을 반복해서 돌리고, 새 발견이 두 차례 연속 나오지 않을 때 비로소 멈춥니다. "10개 찾으면 끝" 같은 고정 횟수로는 놓치는 꼬리까지 긁어냅니다.

요청 예"새로 찾은 문제가 두 번 연속 없을 때까지 계속 찾아 줘"

6다각도 수색 (Multi-modal sweep)
한 가지 검색 방식으로 부족할 때 씁니다

같은 대상을 서로 다른 방법으로 동시에 수색합니다. 각자는 다른 쪽이 뭘 찾았는지 모른 채 움직이고, 한 방식이 못 찾는 것을 다른 방식이 건져 올립니다.

요청 예"파일 구조, 본문, 고유명사, 시간 순서로 나눠 동시에 찾아 줘"

에이전트 줄이기

팀을 꾸리기 전에, 한 에이전트로 충분한지 먼저 확인합니다2026.10

Anthropic Applied AI 팀이 기업 배포 사례를 비교해 공개한 가이드입니다

여러 기업 사례를 비교한 결과, 한 에이전트에 스킬과 도구를 연결한 구조가 서브에이전트 여러 개로 나눈 구조보다 품질이 높은 경우가 많았습니다. 작업당 비용과 지연 시간도 더 낮았습니다. 그래서 기본값은 한 에이전트이고, 나눌 이유가 확인된 단계만 나눕니다.

모델 성능도 이유입니다. Opus 4.5부터 모델이 한 루프 안에서 처리하는 작업량이 예상보다 커졌고, 스스로 진행 상황을 알리고 결과를 점검하게 되었습니다. 예전 모델을 보완하려고 만든 구조가 이제는 필요 없는 경우가 많습니다. 구조가 고정되어 있으면 새 모델로 바꿔도 성능 향상을 얻지 못합니다.

약 2배멀티 에이전트 구조를 단일 루프로 바꾼 한 고객사의 실행 속도 향상
80% 이상스킬과 도구를 필요할 때만 불러오게 바꿔 줄인 Claude Code 시스템 프롬프트 분량 (고급 모델 기준)
30~50개시스템 프롬프트의 도구 정의가 이 수를 넘으면 도구 선택 품질이 떨어집니다

에이전트가 많을 때 생기는 문제 네 가지

큰 조직에서 서브에이전트를 늘렸을 때 반복해서 나타난 현상입니다

1 전달 손실

에이전트 사이에 맥락을 넘길 때마다 세부 정보가 빠집니다. 전달 단계가 늘수록 처음 정보와 멀어집니다.

2 에이전트 난립

팀마다 에이전트를 만들면 역할이 겹치는 에이전트가 수백 개까지 늘어납니다. 공통 기준도 담당자도 없습니다.

3 지시 충돌

팀마다 시스템 프롬프트에 문장을 추가하면 규칙끼리 충돌하고, 답변의 말투도 일관되지 않습니다.

4 평가 범위 축소와 지연

팀마다 자기 단계의 점수만 올리고, 전체 품질은 아무도 측정하지 않습니다. 단계가 늘어난 만큼 응답도 느려집니다.

조직도를 본뜨지 않습니다

기업은 팀마다 에이전트를 하나씩 맡기는 경우가 많아 에이전트 구조가 조직도를 닮습니다. 원문은 이를 콘웨이의 법칙이 작동한 결과로 봅니다. 나눌 때는 부서나 문제 유형이 아니라 맥락 단위로 나눕니다.

나누는 경우는 세 가지입니다

이 중 하나에 해당할 때만 서브에이전트를 둡니다

1 컨텍스트 과부하가 측정됨

한 에이전트에 작업을 모았더니 평가 점수가 실제로 떨어질 때입니다. 인상이 아니라 측정 결과로 판단합니다.

2 병렬 작업

여러 작업을 동시에 처리하고, 끝나면 버려도 되는 새 컨텍스트가 필요할 때입니다.

3 도구 선택 실패, 지시 충돌

한 에이전트가 맞는 도구를 고르지 못하거나, 시스템 프롬프트 안의 지시가 서로 충돌할 때입니다.

나누기 좋은 작업

나머지 시스템에서 받을 정보가 적고, 짧은 결과만 돌려주는 작업입니다. 원문은 서로 독립된 조사, 경계가 분명한 부품, 결과만 보는 검증을 예로 듭니다.

앞 장의 패턴과 연결하면

여섯 패턴 가운데 펼치고 합치기(서로 독립된 조사를 병렬로 처리)와 적대적 검증(만든 에이전트와 분리된 검증)이 이 기준에 맞습니다. 자기 결과를 자기가 채점하면 점수가 후해지므로, 검증은 여전히 나누는 편이 낫습니다.

에이전트 대신 담을 곳

서브에이전트가 하던 작업을 성격에 맞는 자리로 옮깁니다

옮길 내용담을 곳방식
단계, 규칙, 판단 기준 (전문 에이전트의 프롬프트가 담던 내용)스킬평소에는 짧은 설명만 보이고, 필요할 때 전체 내용을 불러옵니다
실행, 실시간 조회, 승인과 검증 같은 고정 절차도구 (MCP)API 하나에 도구 하나가 아니라 사용자 의도 단위로 묶습니다. 사용자별 권한도 도구 안에서 확인합니다
정책, 지표 정의, 제품 사양 같은 참고 자료지식 베이스검색 도구 뒤에 두거나 스킬의 참고 파일로 넣습니다. 코드가 미리 프롬프트에 붙여 넣지 않습니다
항상 필요한 값 불러오기, 형식 변환코드판단이 필요 없는 기계적 처리만 남깁니다

조직의 역할도 바뀝니다. 각 팀은 에이전트 대신 스킬과 도구를 소유하고, 작은 중앙 팀이 시스템 프롬프트와 전체 품질을 책임집니다.

한 번에 하나씩 바꾸고 측정합니다

평가 없이 합치면 무엇이 깨졌는지 알 수 없습니다

1
평가 세트를 먼저 만듭니다

골든 예시 10개면 시작할 수 있습니다. 최종 답변은 루브릭으로 채점하고, 맞는 스킬을 불러왔는지와 맞는 도구를 호출했는지도 확인합니다.

2
자주 함께 쓰이는 에이전트부터 합칩니다

서로의 결과를 이어받거나, 같은 데이터를 다루거나, 자주 함께 호출되는 에이전트가 우선 대상입니다. 바로 합치기 어려우면 메인 에이전트가 도구처럼 호출하게 바꿔 기준 점수부터 확보합니다.

3
합치기 전후 점수를 비교합니다

최종 점수만 보지 않고 어떤 과제의 결과가 바뀌었는지 확인합니다. 합친 버전의 점수가 낮으면 서브에이전트로 되돌립니다.

4
같은 과제를 두 번 이상 실행합니다

Anthropic이 지원 에이전트로 시험했을 때, 서브에이전트 하나를 합치자 지연 시간은 줄었지만 통과하던 절차 하나가 실패했습니다. 메인 에이전트가 주문 조회 도구로 직접 답하면서 배송 담당 에이전트에게 배송일을 확인하지 않은 것입니다. 이 오류는 두 번 실행에 한 번만 나타났습니다.

다이내믹 워크플로우에 적용하면
  • 요청에 "한 에이전트로 충분한 단계는 나누지 마라"를 적고, /config의 크기 설정을 small로 두어 팀 규모를 작게 시작합니다
  • 나누는 단계는 검증과 독립된 조사처럼 짧은 결과만 돌려받는 작업으로 한정합니다
  • 같은 작업을 두 번 실행해 결과가 같은지 확인한 뒤 범위를 넓힙니다

측정하고, 한 번에 하나만 바꾸고, 효과가 확인된 것만 유지합니다.
모델이 좋아질수록 서브에이전트가 맡던 작업은 스킬과 도구로 옮겨 갑니다.

Claude Code에서 다이내믹 워크플로우를 실행합니다

모든 유료 플랜에서 사용할 수 있습니다. Pro는 /config의 Dynamic workflows 항목을 켭니다

1
내장 워크플로우로 먼저 확인합니다

/deep-research 뒤에 질문을 적습니다. 여러 관점으로 검색을 펼치고, 찾은 출처를 서로 대조한 뒤 인용이 달린 보고서 한 편을 돌려줍니다. 교차 확인을 통과하지 못한 주장은 보고서에서 빠집니다.

2
내 작업을 워크플로우로 요청합니다

요청에 "다이내믹 워크플로우로 진행해 줘"처럼 직접 적거나, 맨 앞에 ultracode 키워드를 붙입니다. Claude가 작업 절차를 스크립트로 작성하고, 실행 전에 단계 계획을 보여 주며 승인을 받습니다.

3
/workflows로 진행 상황을 봅니다

실행은 백그라운드에서 진행되고 대화창은 계속 쓸 수 있습니다. /workflows를 열면 단계별 에이전트 수와 각 에이전트의 결과, 토큰 사용량이 보입니다. p로 일시정지, x로 중단합니다.

4
반복할 작업이면 저장합니다

/workflows에서 실행을 고르고 s를 누릅니다. 프로젝트의 .claude/workflows/에 저장하면 팀이 함께 쓰고, ~/.claude/workflows/에 저장하면 나만 씁니다. 다음부터는 /이름으로 같은 절차를 다시 실행합니다.

실행 전에 확인할 것
  • 워크플로우는 실행 도중 사람의 입력을 받지 않습니다. 승인이 필요한 지점이 있으면 그 앞뒤를 별도 워크플로우로 나눕니다
  • 큰 작업은 폴더 하나, 질문 하나처럼 작은 범위로 먼저 실행해 사용량을 확인합니다
  • 에이전트가 25개를 넘거나 예상 토큰이 150만을 넘으면 Large workflow 경고가 뜹니다. 규모 기준은 /config의 크기 설정(small 5개 미만, medium 10개 미만)으로 조절합니다

복사해서 바로 쓰는 요청 템플릿

나누는 방식과 범위를 적어 두면 Claude가 그 기준으로 팀을 설계합니다

Codex에는 다이내믹 워크플로우가 없습니다. 서브에이전트로 역할을 나눠 병렬로 실행합니다. explorer와 worker는 내장 역할이라 미리 만들어 둘 것이 없습니다.

  · 검수는 관점별(수치와 출처, 오탈자, 깨진 링크, 논리)로 펼쳐서 병렬로 돌려라
  · 발견마다 찾지 않은 에이전트가 적대적으로 검증하게 하라
  · 한 에이전트로 충분한 단계는 나누지 마라

# 범위와 마무리

  · 검증을 통과한 발견만 하나의 목록으로 보고하라

FAQ

자주 묻는 질문

다이내믹 워크플로우를 처음 쓸 때 가장 많이 나오는 질문들

에이전트는 많을수록 좋습니까?
아닙니다. Anthropic이 기업 배포 사례를 비교했을 때 한 에이전트에 스킬과 도구를 연결한 구조가 서브에이전트를 여럿 둔 구조보다 품질이 높은 경우가 많았고, 비용과 지연 시간도 낮았습니다. 서브에이전트는 검증, 병렬 조사처럼 짧은 결과만 돌려받는 작업에 둡니다. 판단 기준은 「에이전트 줄이기」에 정리했습니다.
비용은 얼마나 듭니까?
에이전트를 여럿 띄우는 만큼 일반 대화보다 토큰을 몇 배에서 수십 배까지 씁니다. 그래서 모든 일에 걸지 않고, 결과의 가치가 비용을 넘어서는 작업에만 겁니다. 자료 전체 검수, 대규모 문서 정리, 여러 출처 교차 확인 같은 일이 여기에 해당합니다. 처음에는 작은 범위로 한 번 실행해 /workflows에서 에이전트별 토큰 사용량을 확인한 뒤 범위를 넓히는 편이 안전합니다.
/goal과는 어떻게 다릅니까?
/goal은 언제 끝낼지를 거는 명령이고, 다이내믹 워크플로우는 작업을 여러 에이전트에 어떻게 나눌지를 정하는 방식입니다. /goal은 루프 엔지니어링에서 다룹니다.
Codex에서도 쓸 수 있습니까?
Codex에는 같은 기능이 없습니다. 대신 서브에이전트(2026년 3월 16일 정식 출시)로 역할을 나눠 병렬로 실행합니다. 역할과 배치는 요청에 직접 적습니다.
