제안만 하는 AI는 루프가 아닙니다.

실행하고 결과를 확인한 뒤, 수정해서 다시 실행해야 루프입니다.

운영 점검운영 중 확인
품질과 비용을 함께 관리합니다

자동으로 실행된다고 결과가 좋아지지는 않습니다. 루프를 돌리면 기존 코드, 문서, 검증 절차, 비용 예산의 장단점이 그대로 커집니다.

품질 관리
  • 코드베이스와 문서를 깨끗하게 유지
  • 검증 절차를 Skill·체크리스트로 기록
  • 최신 공식 문서를 바로 찾도록 연결
  • 작성 에이전트와 리뷰 에이전트 분리
토큰 관리
  • 작업에 맞는 루프와 모델 선택
  • 성공 조건과 멈춤 조건을 구체적으로 설정
  • 큰 실행 전에 작은 범위로 시험
  • 결과가 정해진 반복 작업은 스크립트로 처리
운영 점검세 가지 원칙
검증, 반영, 사용량

Trigger와 Stop을 정했다면, 루프가 제대로 작동하는지 세 가지 원칙으로 점검합니다.

1
검증은 분리합니다

작업한 에이전트가 직접 합격 여부를 판정하면 평가가 후해집니다. 작성자와 검토자를 분리하고, 가능하면 별도의 채점 루브릭을 둡니다.

2
실패를 시스템에 반영합니다

한 번 수정하고 끝내지 않습니다. 같은 문제가 다음 회차에 반복되지 않도록 규칙, Skill, 체크리스트에 반영합니다.

3
사용량을 봅니다

/usage, /goal, /workflows 같은 명령으로 Skill, 서브에이전트, MCP별 비용을 확인합니다.

실행법명령어 고르기
/goal, /loop, /schedule

목표가 분명하면 /goal, 로컬에서 주기적으로 확인하려면 /loop을 씁니다. 클라우드에서 예약 실행하려면 /schedule을 씁니다.

/goal
완료 기준이 있을 때

점수, 테스트 통과, 체크리스트처럼 완료를 판정할 수 있는 작업에 씁니다.

/loop
정해진 간격으로 확인할 때

로컬 컴퓨터에서 PR, 리뷰, CI처럼 외부 상태가 바뀌는 작업을 주기적으로 확인합니다.

/schedule
클라우드에서 돌릴 때

컴퓨터가 꺼져 있어도 정해진 시각에 실행해야 하는 작업은 클라우드 예약(Routines)으로 옮깁니다.

별칭 /routines

Routines/loop은 컴퓨터가 꺼지면 멈춥니다. 무인 실행이 필요하면 Routines로 옮깁니다.

자동 실행과 최종 결정은 분리
한 루프의 기본 순서

의도 › 맥락 › 실행 › 관찰 › 조정. 이 다섯 단계가 한 루프입니다. 목표를 달성하거나 멈춤 조건에 도달할 때까지 이 단계를 반복합니다. 제안만 하는 AI는 루프가 아닙니다. 실행하고 결과를 확인한 뒤, 수정해서 다시 실행해야 루프입니다.

운영 점검

품질과 비용은 루프를 운영하면서 점검합니다

Trigger와 Stop을 정했다면 루프가 제대로 작동하는지 점검해야 합니다. 자동으로 실행된다고 결과가 좋아지지는 않습니다. 루프를 돌리면 기존 코드, 문서, 검증 절차, 비용 예산의 장단점이 그대로 커집니다.

품질 관리

  • 코드베이스와 문서를 깨끗하게 유지
  • 검증 절차를 Skill·체크리스트로 기록
  • 최신 공식 문서를 바로 찾도록 연결
  • 작성 에이전트와 리뷰 에이전트 분리

토큰 관리

  • 작업에 맞는 루프와 모델 선택
  • 성공 조건과 멈춤 조건을 구체적으로 설정
  • 큰 실행 전에 작은 범위로 시험
  • 결과가 정해진 반복 작업은 스크립트로 처리
1
검증은 분리합니다
작업한 에이전트가 직접 합격 여부를 판정하면 평가가 후해집니다. 작성자와 검토자를 분리하고, 가능하면 별도의 채점 루브릭을 둡니다.
2
실패를 시스템에 반영합니다
한 번 수정하고 끝내지 않습니다. 같은 문제가 다음 회차에 반복되지 않도록 규칙, Skill, 체크리스트에 반영합니다.
3
사용량을 봅니다
/usage, /goal, /workflows 같은 명령으로 Skill, 서브에이전트, MCP별 비용을 확인합니다.
실행법

/goal, /loop, /schedule을 구분해서 씁니다

목표가 분명하면 /goal을 씁니다. 로컬 컴퓨터에서 주기적으로 확인하려면 /loop을 씁니다. 클라우드에서 정해진 시각에 실행하려면 /schedule 또는 Routines를 씁니다. Proactive 루프는 여기에 동적 워크플로우와 자동 모드를 추가해 구성합니다.

1
완료 기준이 있으면 /goal
점수, 테스트 통과, 체크리스트처럼 완료를 판정할 수 있는 작업에 씁니다.
2
정해진 간격으로 확인하면 /loop
로컬 컴퓨터에서 PR, 리뷰, CI처럼 외부 상태가 바뀌는 작업을 주기적으로 확인합니다.
3
클라우드에서 실행하면 /schedule 또는 Routines
컴퓨터가 꺼져 있어도 정해진 시각에 실행해야 하는 작업은 클라우드 예약으로 옮깁니다.
클라우드로 옮기면 Routines입니다

/loop은 지금 켜 둔 컴퓨터에서 실행되므로 컴퓨터가 꺼지면 멈춥니다. 사람이 없어도 정해진 시각에 클라우드에서 실행하려면 Routines 예약 실행으로 옮깁니다.

루프 엔지니어링의 출발점

“As big as the step from source code to agents was, loops are just as important and as big a step.”

소스 코드에서 에이전트로 넘어간 것이 큰 도약이었던 만큼, 루프도 그만큼 중요하고 큰 도약입니다. 그는 이제 프롬프트를 직접 쓰지 않고, 루프가 Claude에게 작업을 지시하게 한다고 말합니다. 이 페이지가 다루는 루프 엔지니어링은 이 발언에서 출발했습니다.

/goal 실습

지시가 아니라 목표를 선언합니다

일반적인 지시는 "이것을 해 주세요"입니다. Claude·Codex가 답을 한 번 내놓으면 작업이 끝납니다. /goal은 종료 기준 자체를 바꿉니다. 목표를 선언하면 Claude·Codex는 "답을 다 했습니다"가 아니라 "조건이 달성됐습니다"를 종료 기준으로 삼습니다. 멈추려 할 때마다 목표 달성 여부를 검사받으므로 중간에 멈추지 않고 끝까지 진행합니다.

지시: 한 번 답하면 끝

"보고서 초안 주세요"
  • 초안 하나를 내놓으면 작업 종료
  • 품질이 기준에 맞는지는 확인하지 않음
  • 부족하면 사람이 다시 지시해야 함

목표 선언: 조건 달성까지

"이번 분기 시장 조사 자료를 임원 보고 수준으로 정리하라"
  • 멈추려 할 때마다 달성 여부를 검사받음
  • 미달이면 스스로 다음 작업을 이어감
  • 사람은 목표와 최종 판정만 맡음
한 문장으로

/goal은 "무엇을 해라"가 아니라 "어떤 상태가 되면 완료로 인정하겠다"를 정하는 명령입니다. 작업 단위가 답변 한 개에서 목표 달성으로 바뀝니다.

Claude Code와 Codex에서 /goal을 활용해 봅니다

이 실습에서는 목표 문장 하나를 다듬습니다

1
Claude Code나 Codex를 열고 /goal을 입력합니다

슬래시 명령창에 /goal을 입력하고 목표 문장을 적습니다. 두 도구의 명령 이름은 같고, Codex에서는 /goal pause, resume, clear로 일시 정지, 재개, 해제합니다. /goal은 Codex에 2026년 4월 30일(v0.128.0), Claude Code에 5월 11일(v2.1.139) 추가됐습니다. Codex에서는 실험 기능으로 시작해 5월 21일(v0.133.0)부터 기본으로 켜졌습니다. 설치하지 않았다면 바이브 코딩 101에서 먼저 설치합니다.

2
목표 문장을 검증 가능하게 적습니다

좋은 목표 문장의 조건은 세 가지입니다. 완료 검증 가능(완료 여부를 기계적으로 판정), 품질 기준 명시(어느 수준이면 합격인지), 범위 명시(어디까지 수정해도 되는지).

3
중간 보고를 받습니다

문제를 모두 찾은 시점, 수정 계획을 세운 시점처럼 방향을 점검할 지점에서 보고하게 합니다. 진행 중에도 사람이 개입할 지점을 미리 정해 둡니다.

4
최종 승인은 사람이 합니다

목표 달성 보고가 오면 결과를 직접 확인하고 판정합니다. 실행은 맡기되 판단은 사람이 하는 것이 /goal 사용의 기본 원칙입니다.

나쁜 목표 문장

"이 자료 좀 더 좋게 만들어줘"
  • "좋게"가 무엇인지 판정할 수 없음
  • 품질 기준이 없어 어디서든 멈출 수 있음
  • 범위가 없어 관계없는 파일까지 수정할 수 있음

좋은 목표 문장

"이 폴더의 시장 조사 자료를 임원 보고 수준으로 정리하라. 수치마다 출처가 있고, 오탈자와 깨진 링크가 0건이면 완료다. 이 폴더 밖은 건드리지 마라"
  • 완료 조건을 기계적으로 판정 가능
  • 품질 기준이 숫자로 명시됨
  • 수정 범위가 분명함
완료 판정 체크리스트
  • 완료 조건을 항목별로 대조했다. 하나라도 미달이면 완료가 아니다
  • 수정된 파일이 목표에 명시한 범위 안에 있다
  • 수치와 출처는 보고에 의존하지 않고 원본에서 확인했다
  • 발송, 배포, 결제 등 되돌릴 수 없는 동작은 사람 승인을 거쳤다

복사해서 바로 쓰는 /goal 템플릿

목표, 완료 조건, 범위는 두 도구가 같고 진행 방식만 다릅니다

Codex 템플릿에 나오는 explorer와 worker는 내장 역할이라 따로 만들 필요가 없습니다. 그 밖의 역할이 필요할 때만 ~/.codex/agents/에 정의합니다.

Claude Code 템플릿 
/goal (달성할 목표를 한 줄로 적는다)
  예) 이 폴더의 시장 조사 자료를 임원 보고 수준으로 정리하라

# 완료 조건 (모두 충족해야 완료다)
  · 모든 수치에 출처가 달려 있다
  · 오탈자와 깨진 링크가 0건이다
  · 페이지마다 핵심 메시지가 첫 화면에 보인다

# 범위
  · 이 폴더 안의 파일만 수정한다. 다른 폴더는 건드리지 않는다

# 진행 방식
  · 이 작업에 맞는 동적 워크플로우를 직접 설계해 실행하라
  · 한 에이전트로 충분한 단계는 나누지 마라. 나누는 단계는 검증과 독립된 조사처럼 짧은 결과만 돌려받는 작업으로 한정하라
  · 검수는 관점별로 나눠 병렬로 실행하고, 수정본은 수정하지 않은 에이전트가 적대적으로 검증하게 하라
  · 문제를 모두 찾으면 통합 보고를 먼저 하고, 수정은 승인 후 진행하라

# 완료 조건 (모두 충족해야 완료다)
  · 모든 수치에 출처가 달려 있다
  · 오탈자와 깨진 링크가 0건이다
  · 페이지마다 핵심 메시지가 첫 화면에 보인다

# 범위
  · 이 폴더 안의 파일만 수정한다. 다른 폴더는 건드리지 않는다

# 진행 방식 (배치를 직접 지정한다)
  · 에이전트는 아래 단계에서만 실행하고, 그 밖의 작업은 메인 에이전트가 직접 처리하라
  · 검수는 explorer 에이전트를 관점별로 나눠 병렬로 실행하라
  · 수정은 worker 에이전트에 파일 단위로 맡겨라
  · 수정본은 수정을 맡지 않은 에이전트가 다시 검증하게 하라

FAQ

자주 묻는 질문

/goal을 처음 쓸 때 자주 나오는 질문

일반 대화와 무엇이 다릅니까?
일반 대화는 한 세션 안에서 묻고 답하면 끝납니다. /goal은 종료 조건을 정해 두고 그 조건을 달성할 때까지 실행과 검증을 반복합니다. 짧은 질문은 대화로 하고, 끝까지 완수해야 하는 큰 작업은 /goal로 맡깁니다.
진행 중에 멈추거나 방향을 바꿀 수 있습니까?
가능합니다. 목표 문장에 중간 보고 지점을 적어 두면 그 시점마다 사람이 진행 상황을 확인하고 방향을 조정할 수 있습니다. 보고 시점이 아니어도 언제든 직접 개입해 작업을 멈추거나 지시를 추가할 수 있습니다.
틀리면 누가 책임집니까?
사람입니다. /goal은 실행을 맡기는 기능이지 판단까지 맡기는 기능이 아닙니다. 그래서 중간 보고 지점과 최종 승인 단계를 목표 문장에 미리 적어 둡니다. 사람의 최종 판정 없이는 결과를 내보내지 않는 것이 원칙입니다.
어디까지 맡겨도 됩니까?
되돌릴 수 있는 일은 넓게, 되돌릴 수 없는 일은 좁게 맡깁니다. 문서 작성, 코드 수정, 분석처럼 결과를 검토하고 되돌릴 수 있는 작업은 끝까지 맡겨도 됩니다. 발송, 배포, 결제처럼 되돌리기 어려운 동작은 반드시 사람의 승인을 거칩니다.
